## 3. 做得好的地方

### 3.1 协议执行语义被逐步固定，而非在 UI 中隐式生长

- `ProtocolDocument/ProtocolTrial` 保持 frozen；trial index、retry、mode override、epoch 和 pending command 都进入执行态。
- manual/TTL 与呼吸门控是串联的两道门：trigger 只进入 `WAITING_EXHALE`，只有校准后的合法 EXHALE 样本才提交 open。
- `timing_ms` 仍只解析/展示，没有被 3.4 静默赋予 onset 语义。这避免了以性能改造之名改变实验协议含义。
- 动作前 readiness 不足是无副作用拒绝；运行中 readiness 丢失是安全事件，必须 invalidate epoch、进入 `BLOCKED` 并收敛硬件。

### 3.2 TTL 从“收到 signal”变成了可证明的输入契约

- Dev1 的 AI0/AI6 使用唯一 continuous Analog Input task，避免 NI `resource reserved/-50103`。
- AI0/AI6 显式 RSE；AI6 使用高低阈值迟滞、去抖、持续高电平单次发射和低电平重新布防。
- pulse 在采样/发射时捕获 immutable `arm_epoch`、`sequence`、wall timestamp 和 monotonic identity；Controller 不给旧事件补当前 epoch。
- AI6 不可用时允许 AI0-only/manual 安全降级；运行中的共享 AI read error 则 fail closed，不能伪装成“无脉冲”。

### 3.3 低抖动不是调参，而是所有权与测量点重构

- `expected_open_ns` 来自实际触发判定使用的呼吸样本；`actual_*_ns` 来自 HAL 在 DO write 前后采集的 `daqmx_write_ack`。
- close deadline 固定为 `actual_open_ns + duration_ns`，保证 late open 不会缩短正常刺激时长。
- `ActuationWorker` 成为 executor、gating、metrics 与 DO 的唯一 owner；HardwareWorker 只拥有 AI，FlowWorker 只拥有 serial。
- deadline queue、紧急队列、stable sequence、generation/latch 和 persistent DO task 共同消除了 UI event loop、跨线程 task 与重复创建 task 的长尾。
- p95 使用明确的 nearest-rank、最近 100 个样本、20 样本门槛和严格 20/30ms 边界；失败、stale 和 safety receipt 不混入正常质量样本。

### 3.4 Session writer 把数据完整性纳入安全状态

- `.raw/.log/manifest` 在隐藏 `.session.part` 目录中成对建立，完成后以单目录 rename 发布。
- Hardware/Actuation owner 使用 O(1) `put_nowait` 直投 immutable envelope；Qt signal 只服务 UI，不是持久化必经路径。
- Hardware、Actuation、Controller 三个 producer fence 是 finalization barrier；“队列暂时为空”不等于记录结束。
- raw/log 的 byte、count、SHA-256、session sequence 和 producer sequence 均由 writer/validator 流式核对。
- queue full、I/O、fsync、close、manifest 或 rename 任一步失败都会锁存 recorder failure，先使 `recording_ready=False`，再唤醒动作 owner；危险普通动作被阻断，SAFETY close 保持可用。

### 3.5 对抗式 review 和失败 HIL 被当作设计输入

- Story 3.3–3.5 的复审没有用“测试全绿”替代竞态证明，而是持续补齐 stale pulse、owner handoff、queue full、publish rollback、close timeout、fence 顺序等契约。
- 两次 Story 3.5 HIL 失败没有被挑选成功 run 掩盖：
  - 首个 open `33.0973ms` 暴露 trigger cutover 前历史 AI backlog。
  - valve 9 close `30.3166ms` 暴露 owner dispatch 与 diagnostic I/O 干扰，以及 severe 分支自身全关契约缺口。
- 修复均保持首个正式样本、统计口径和阈值不变，最终以新 candidate 完成单次正式验收。

## 4. 挑战与成长点

### 4.1 上游 Story 的功能描述不足以表达并发系统

Epic 原始验收只说明 manual/TTL、<20ms 和文件输出，未直接定义 owner、epoch、command identity、fence、generation 或 publish commit point。大量复杂度是在实现与对抗式 review 中才被发现。

经验：凡涉及硬件、跨线程、队列或持久化，Story AC 必须同时定义：

- 唯一可变状态 owner；
- immutable intent/command/result identity；
- 正常、取消、stale、uncertain 和 failure 的终态；
- shutdown/finalize barrier；
- 恢复是否显式、是否可重试、是否允许自动继续。

### 4.2 Windows 调度行为不能由平均值或 Mock 推断

- 受限 Codex 沙箱阻断 NI 本机 IPC，曾制造 `DAQmxCreateTask` 假超时；真实用户环境立即返回。
- `QThread.msleep(1)` 在现场表现出约 15–20ms 粗粒度，足以破坏目标。
- 首动作和 close 尾延迟主要出现在 DAQ write 之前，说明瓶颈在 owner 调度、消息优先级与 backlog，而不是 NI write ack。

经验：环境身份、线程等待原语、首样本、rolling p95 和分段 trace 都必须成为 HIL 证据的一部分。

### 4.3 “完成关闭”比“请求关闭”更难

stop、LOW_FLOW、severe、shutdown、协议替换和 recorder failure 都需要从逻辑 invalidation 走到每个配置目标的真实 close receipt，并处理 stale/duplicate/uncertain 结果。任何只看 UI snapshot 或函数返回的方案都会过早宣布安全。

经验：安全关闭必须以配置目标集合、receipt 集合和 owner handoff 三者共同确认。

### 4.4 文件恢复不能依赖目录名猜测

仅凭 `.session.part`、同名 raw/log 或 manifest 文件名会误伤用户目录。最终方案需要 ownership marker、schema/version/session identity、bounded/cancellable streaming validator 和 recovery-required marker。

经验：recovery 的第一原则是“只处理可证明由本程序拥有的对象”，第二原则是“不自动冒充完成或续写”。

### 4.5 工具配置与项目真实 artifact 路径发生漂移

项目真实状态源是 `docs/sprint-artifacts/sprint-status.yaml`，历史 Story/retro 也位于该目录；但 `_bmad/bmm/config.yaml` 仍把 planning/implementation artifacts 指向基本为空的 `_bmad-output`。本次复盘依赖 `project-context.md` 才避免写入错误位置。

经验：工作流配置本身也属于可维护性边界，必须与项目权威状态源一致。

## 5. 确定性并发测试经验

本 Epic 最有价值的测试实践是把竞态变成可重复的状态排列，而不是增加真实 `sleep`：

- fake monotonic clock：deadline 不提前、相同 deadline 稳定排序、retry token、wall-clock 跳变。
- Event/Barrier：safety loss during blocking write、stop vs ack、close timeout vs late complete、publish vs rollback failure。
- immutable identity：旧 TTL epoch、跨协议 pulse、stale successful open、duplicate/conflicting receipt。
- queue/fence：normal queue full、emergency capacity、fence 不越过早先 action/receipt、producer sequence 不跳号。
- generation/cancellation token：recorder bind timeout、旧 finalizer、旧 recovery worker、旧 recorder failure 不污染新会话。
- fake filesystem/fault injection：raw/log/header/flush/fsync/close/manifest/rename 全阶段失败，任何失败都不得产生可认证 final bundle。

这些测试形成 Epic 4 的默认并发测试模板；新增跨 owner 功能不得退回依赖真实调度概率的测试。

## 9. Epic 4 不可妥协的技术约束

### C1. Owner topology 是架构不变量

- HardwareWorker：唯一 AI0/AI6 task owner。
- ActuationWorker：唯一 `ProtocolExecutor/GatingService/metrics` 与全部 DO owner。
- FlowWorker：唯一 Alicat serial owner。
- SessionWriterWorker：唯一 raw/log/manifest 文件 owner。
- Controller 只编排 immutable intent/result；View 只发意图和渲染 snapshot。
- Epic 4 禁止从 View、Controller、临时线程或 timer 直接调用 HAL、serial 或同步磁盘 I/O。

### C2. 清洗必须是显式业务类别，禁止冒充 SAFETY

- Story 4.1 应新增受控 `CLEANING`/maintenance action category 或等价类型。
- 清洗 open 不是 safety close，不能用 SAFETY 类别绕过 recording、lease 或 interlock。
- 清洗运行必须独占设备 lease，拒绝协议、manual/pretest 和补偿流程并发 open。
- 清洗 receipt 不进入协议正常 jitter 质量窗口，但必须保留 command identity、target、ack、result 和步骤事件。
- 开发前必须决定并写入 AC：清洗使用独立 maintenance bundle，还是复用 session bundle 的明确 maintenance 模式；任何一种都必须 fail closed 且可审计。

### C3. 清洗与补偿流程必须由 owner 状态机和单调 deadline 驱动

- 不使用 UI `QTimer`、`sleep` 或 ad-hoc `threading.Thread` 编排步骤。
- 每一步都必须有 immutable command、generation/epoch、receipt 和失败终态。
- stop、LOW_FLOW、disconnect、recorder/owner failure 可抢占普通步骤，并收敛 21 个配置目标。
- stale/late flow 或 valve receipt 不得推进新步骤。

### C4. Story 4.4 必须保持“先流量确认，再主阀/气味阀”的业务顺序

- MFC setpoint 只能通过 FlowWorker；动作许可先经 ActuationWorker 的 lease/interlock。
- 必须等待匹配 generation/command identity 的成功 flow receipt，再提交对应主阀/气味阀动作。
- flow failure、timeout、epoch drift 或 serial owner failure均 fail closed。
- 不得把 MFC write、主阀 task cold start 或日志 I/O放入 odor open deadline。
- 4.4 的阶段事件必须进入当前 session 结构化日志，但不得重置 session 或质量窗口。

### C5. 配置更新必须是断开态原子事务

- Story 4.2 只允许在无 active/possibly-open valve、无活动 session、无 owner lease、worker 已安全交接的状态应用 NI/COM 变更。
- 校验成功前不得部分写入运行时配置；应用失败保留旧的有效配置并保持 fail-closed。
- 配置源继续是 `default_config.json + local_config.json` 递归覆盖，不新增第二真源。
- Dev1/Dev2 是当前生产必需设备；Dev3 只有在铭牌、NI MAX 和用途经用户确认后才可由本机覆盖显式加入。
- 配置 UI 必须验证设备别名、型号、通道映射、主阀 target 与串口，不允许错误 ID 直接进入 HAL。

### C6. Recorder readiness 继续是危险动作前置条件

- NORMAL/MANUAL/PRETEST/WARMUP 及未来 CLEANING 的记录策略必须显式定义，不能出现 owner 内部绕过。
- recorder queue full/I/O failure 先锁存 `recording_ready=False`，再唤醒动作 owner。
- 记录失败不阻断 SAFETY close，但任何失败会话都不得发布 complete bundle或原地续写。

### C7. Fail-closed 与显式恢复语义不得弱化

- write/ack 不确定即 `possibly_open`；只有成功 close receipt 才能清除。
- queue full、owner handoff failure、stale generation、readiness loss 和 shutdown failure 都必须保守阻断。
- safe telemetry 不自动清除 unsafe latch；恢复需要 owner 确认阀门已关、readiness 已恢复和用户显式动作。
- recovery 只隔离、验证和报告本程序可证明拥有的数据，不自动补全、删除或续写。

### C8. 任何跨线程交错都要有确定性测试

- 使用 fake clock、Event、Barrier、cancellation token、fake filesystem 和 fault injection。
- 禁止以毫秒级 `sleep` 或“多跑几次没失败”作为唯一竞态证明。
- Epic 4 至少覆盖：cleaning step vs stop、flow ack vs epoch invalidation、config apply vs owner handoff、session finalize vs shutdown、queue full vs emergency close、late receipt vs next phase。

### C9. HIL Gate 由变更范围触发

- 凡修改 ActuationWorker、HardwareWorker、FlowWorker、SessionWriter、DO task、AI task、queue priority、interlock、主阀/MFC 编排或 shutdown 顺序，必须重跑对应真实 Windows/NI HIL。
- 触及协议 deadline/owner queue 时，重跑 200 open + 200 close、全部 aggregate/rolling/final-last-100 p95 和四类安全场景。
- 清洗/补偿新增 HIL 使用惰性、无气味、无受试者条件，并验证实际步骤顺序和 21-target 最终全关。
- 不得把 Mock、软件注入或 DAQ write ack 扩大声称为外部传感器、机械阀或破坏性故障证据。

### C10. 本地化是可测试契约

- 所有按钮、状态、错误、恢复与帮助使用简体中文和 UTF-8。
- 错误必须同时说明发生了什么、系统采取了什么安全动作、用户下一步做什么。
- 颜色只辅助，不能替代状态文字。
- Story 4.3 应增加用户可见字符串与乱码回归扫描，并复核协议、文件、恢复、配置和清洗路径。

### C11. `timing_ms` 语义继续冻结

Epic 4 不得顺手让 `ProtocolTrial.timing_ms` 参与执行。若产品需要 onset delay，必须独立定义相对基准、暂停/恢复、TTL/呼吸关系和 jitter 口径，再新增 Story。

### C12. 发布完成与 Epic 完成继续分开证明

Epic 4 开发 Gate 继续使用 pytest、ruff、diff check；实验室交付还必须补充 PyInstaller 干跑、资源清单、打包后 Mock 启动和中文操作/恢复指引。不能用源码 HIL 代替可执行产物验证。

## 11. Critical Path

Epic 4 正式开发前必须完成：

1. A3-01：统一 artifact/state 真源。
2. A3-02：修正 Dev3/USB-6501 需求漂移。
3. A3-03：固定清洗类别、lease、记录与恢复契约。
4. A3-06：确认 Epic 4 的真实硬件复验矩阵。

Story 4.4 开发前还必须完成 A3-04。A3-07/A3-08 属于发布候选门禁，不阻止纯 Story 设计，但不能在实验室交付时继续缺失。

## 12. 团队协议

- 不以 UI capability 代替 service/owner 守卫。
- 不以“已请求关闭”代替“目标集合 receipt 已确认关闭”。
- 不以测试数量代替竞态覆盖，也不以 Mock 代替真实硬件性能证据。
- 不把普通维护动作标记为 SAFETY 来绕过 interlock。
- 不从 logger 文本反解析业务事实；跨边界只传结构化、不可变对象。
- 不自动恢复 unsafe/failed 会话或硬件状态；恢复必须有明确身份、门禁和用户动作。
